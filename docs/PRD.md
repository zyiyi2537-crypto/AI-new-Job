## 1. 产品概述

### 1.1 产品背景

求职者通常需要在 BOSS 直聘、智联招聘、猎聘、拉勾等多个平台重复搜索岗位，再手工完成岗位筛选、JD 对比、简历修改、格式调整和投递记录维护。现有开源项目往往只覆盖其中一个环节：有的只能采集岗位，有的只能优化简历，有的只提供排版工具，缺少一套以真实个人经历为基础的完整闭环。

本产品将多个招聘平台的岗位采集、统一岗位库、可解释匹配评分、岗位定制简历、ATS 检查、PDF/DOCX 导出和投递看板整合为一个本地应用。

### 1.2 产品定位

一句话定位：

> 从多个招聘平台采集岗位，基于用户真实经历进行可解释评分，并为每个目标岗位生成独立、可验证、可编辑的简历版本。

本产品不是无人值守的“海投机器人”。AI 负责整理、分析和起草，用户负责确认事实、选择目标岗位并执行最终投递。

### 1.3 产品目标

1. 将多平台岗位集中到一个可搜索、可筛选、可去重的岗位库。
2. 用统一且可解释的规则判断岗位是否值得申请，而不是只输出一个不可解释的 AI 分数。
3. 建立一份可信的简历母版和经历证据库，为不同岗位生成不同简历版本。
4. 提供可视化排版、ATS 检查和 PDF/DOCX 导出能力。
5. 记录岗位、简历版本、投递状态和后续结果，形成持续优化闭环。

### 1.4 非目标

MVP 不包含以下能力：

- 无人值守批量投递、自动点击“立即沟通”或自动发送简历。
- 未经用户确认自动代表用户与招聘者持续对话。
- 绕过验证码、设备验证或平台访问限制。
- 扫描招聘平台手机 App；首版仅适配平台网页版。
- 编造工作经历、项目、技能、学历、证书或数据指标。
- 企业招聘、候选人管理和 HR 端 ATS 功能。

## 2. 用户与场景

### 2.1 目标用户

| 用户类型 | 核心需求 |
| --- | --- |
| 应届生 | 从课程、比赛和校园项目中提取可用于岗位匹配的真实证据 |
| 社招求职者 | 快速比较大量 JD，并针对高匹配岗位定制简历 |
| 转行求职者 | 区分直接经验、可迁移能力、作品证据和真实缺口 |
| 多方向求职者 | 使用同一事实底稿生成产品、运营、数据、研发等不同版本 |
| 高频投递者 | 管理岗位、简历版本、投递状态和反馈数据 |

### 2.2 核心用户故事

- 作为求职者，我希望一次配置目标城市、薪资和方向，然后从多个平台采集岗位。
- 作为求职者，我希望知道每个岗位为什么得分高或低，以及缺少哪些真实证据。
- 作为求职者，我希望同一段经历针对不同岗位改变重点，但不产生虚假信息。
- 作为求职者，我希望比较原简历和岗位定制版，逐条接受或拒绝修改。
- 作为求职者，我希望导出的 PDF 能被 ATS 解析，且没有空白页、截断或内容溢出。
- 作为求职者，我希望在最终投递前保留人工确认，避免误投和账号风险。

### 3.2 MVP 成功定义

用户能够完成以下闭环：

1. 上传一份现有简历，系统自动解析并生成简历母版；用户无需从空白表单逐项填写。
2. 登录至少两个招聘平台并采集岗位。
3. 查看经过清洗和去重的岗位列表。
4. 查看可解释的岗位评分、优势、缺口和风险。
5. 选择一个岗位生成独立简历版本。
6. 检查修改差异并确认事实。
7. 导出可解析的 PDF 或 DOCX。
8. 打开原岗位页面，人工完成投递并更新状态。

## 4. 核心业务流程

```text
首次启动
  -> 创建本地资料库
  -> 拖拽或选择一份现有简历
  -> 本地解析文本、版面和章节
  -> AI 提取结构化经历事实
  -> 用户批量预览，仅处理低置信度或冲突项
  -> 自动生成第一版简历母版
  -> 补充目标岗位、城市、薪资和排除项

岗位采集
  -> 用户在专用浏览器中登录平台
  -> 选择平台、关键词、城市和采集数量
  -> 读取用户可见的搜索结果和完整 JD
  -> 标准化、去重并写入岗位库

岗位分析
  -> 硬条件过滤
  -> 规则与语义匹配
  -> 经历证据映射
  -> AI 解释和风险检查
  -> 生成总分、子分、置信度和申请建议

简历定制
  -> 用户选择目标岗位
  -> 系统从已确认事实中选择相关证据
  -> AI 提议顺序、摘要和 bullet 修改
  -> 用户查看逐条差异并确认
  -> ATS 与可信度检查
  -> 生成该岗位专属简历版本

投递跟踪
  -> 导出 PDF/DOCX
  -> 打开平台原始岗位链接
  -> 用户人工投递
  -> 记录投递状态、简历版本和反馈
```

## 5. 功能需求

### 5.1 用户画像与简历母版

#### FR-PROFILE-001 简历导入

首次使用的默认入口是“上传我的现有简历”，不是空白个人资料表单。支持拖拽或选择 PDF、DOCX、Markdown、TXT 和 JSON Resume，系统自动提取个人信息、教育、工作、项目、技能、证书和语言能力，并生成可继续维护的第一版简历母版。

导入流程：

1. 用户上传一份原始简历。
2. 系统优先在本地提取文本、章节、时间范围和基础字段。
3. 图片型或无文本层 PDF 启用 OCR，并明确标记 OCR 结果。
4. 系统将内容映射到统一简历结构，保留原始段落与字段之间的引用关系。
5. 用户在“原始简历 / 解析结果”对照界面中批量检查。
6. 高置信度字段默认选中；用户只需处理低置信度、冲突和缺失的关键字段。
7. 用户确认后生成简历母版和经历证据库，随后即可进行岗位匹配。

手工填写只能作为没有现成简历时的备用入口，不得强制用户在上传前逐项填写姓名、教育、工作经历和项目经历。

验收标准：

- 首次启动首屏提供清晰的上传区域，并允许稍后上传或使用空白模板。
- 用户上传一份有效简历后，可以直接得到完整的结构化预览，不需要重复录入已识别信息。
- 用户可以对照原始简历批量接受解析结果，并单独修正错误字段。
- 系统展示章节和字段的识别置信度，只追问影响岗位匹配或最终简历的关键信息。
- 扫描型 PDF 无法可靠识别时启用 OCR；OCR 仍不可靠时展示原文位置并请求用户确认。
- 无法确认的字段标记为“待确认”，不能进入最终简历。
- 原始文件与解析后的结构化数据均保存在本地。
- 手机号、邮箱等敏感字段默认不发送给模型，除非生成最终简历确有需要。

#### FR-PROFILE-002 原始资料管理

用户可以保留一份“当前原始简历”，并可继续上传新版简历、补充作品集、项目说明或证书材料。重新上传时，系统先生成差异，不直接覆盖已经确认的事实。

每份原始资料记录文件哈希、文件类型、导入时间、解析状态、文本提取方式和对应的母版版本。重复上传同一文件时提示用户，不创建重复母版。

#### FR-PROFILE-003 经历证据库

每条事实应包含：事实内容、所属经历、时间、技能标签、指标、证据来源、确认状态和更新时间。

事实状态：

- `confirmed`：用户确认，可进入最终简历。
- `pending`：需要用户补充或确认。
- `inferred`：模型推断，只能用于提问，不得进入最终简历。
- `rejected`：用户否认，不再使用。

#### FR-PROFILE-004 求职偏好

支持配置：目标岗位、城市、远程偏好、薪资下限、行业偏好、公司规模、经验级别、不可接受条件、公司黑名单和关键词黑名单。

### 5.2 平台连接与岗位采集

#### FR-SOURCE-001 平台插件

平台连接采用插件结构，每个平台实现统一能力：

```ts
interface JobSourceAdapter {
  id: string;
  capabilities: SourceCapabilities;
  connect(): Promise<ConnectionState>;
  search(query: SearchQuery): Promise<JobSummary[]>;
  fetchDetail(job: JobSummary): Promise<JobDetail>;
  healthCheck(): Promise<SourceHealth>;
}
```

#### FR-SOURCE-002 登录方式

- 使用平台专用的持久化浏览器配置目录。
- 首次连接由用户扫码或手动登录。
- 不要求用户将完整 Cookie 导出到 JSON 文件。
- 登录过期、验证码或安全验证出现时立即暂停，并提示用户处理。
- 不复制用户日常浏览器中的密码、历史记录和扩展数据。

#### FR-SOURCE-003 首版平台

| 平台 | MVP 能力 | 备注 |
| --- | --- | --- |
| BOSS 直聘 | 关键词、城市、列表、薪资、公司、标签、完整 JD、原链接 | 反自动化最强，必须有头运行并允许失败降级 |
| 智联招聘 | 关键词、城市、列表、薪资、公司、完整 JD、原链接 | 支持登录态和公开结果 |
| 猎聘 | 关键词、城市、列表、薪资、公司、完整 JD、原链接 | P0 |
| 拉勾 | 同上 | P1 |
| 前程无忧 | 同上 | P1 |

#### FR-SOURCE-004 采集任务

用户可选择平台、关键词、城市、页数或最大岗位数。任务展示实时状态：等待登录、采集中、详情补全、已完成、部分成功、验证暂停和失败。

验收标准：

- 单个平台失败不影响其他平台任务。
- 每个任务记录开始时间、结束时间、结果数量、失败原因和平台版本。
- 支持取消任务，不留下损坏的中间数据。
- 默认限速，不并发轰炸平台。
- 同一平台出现验证码或限制提示后停止请求，不自动绕过。

### 5.3 岗位标准化与去重

#### FR-JOB-001 统一岗位模型

不同平台采集结果转换为统一字段：

- 平台与平台岗位 ID
- 岗位名称、公司名称、城市与区域
- 薪资文本、最低薪资、最高薪资、薪资月数
- 经验、学历、岗位类型、发布日期
- 完整 JD、技能标签、公司信息、招聘者活跃信息
- 原始链接、采集时间、最后更新时间和原始数据摘要

#### FR-JOB-002 去重规则

依次使用以下规则去重：

1. 同平台岗位 ID。
2. 规范化后的原始 URL。
3. 公司 + 岗位名称 + 城市 + 薪资区间的组合指纹。
4. 高相似 JD 作为疑似重复，由用户确认合并。

不得自动把不同地点、不同级别或不同业务线的同名岗位合并。

#### FR-JOB-003 岗位状态

岗位状态包括：`new`、`analyzed`、`shortlisted`、`ignored`、`expired`。系统保留历史 JD，不用新内容覆盖旧版本。

### 5.4 岗位匹配与评分

#### FR-MATCH-001 评分结构

岗位总分为 0-100，由确定性规则、语义匹配和 AI 解释共同生成：

| 维度 | 权重 | 说明 |
| --- | ---: | --- |
| 硬条件 | 30 | 学历、经验、城市、薪资、工作方式、必需证书 |
| 技能匹配 | 25 | 技能关键词、同义词和语义匹配 |
| 经历证据 | 20 | 已确认工作、项目和成果对岗位职责的支撑程度 |
| 求职偏好 | 15 | 行业、公司规模、岗位方向、通勤与个人偏好 |
| 岗位质量与风险 | 10 | JD 完整度、职责清晰度、异常关键词、招聘活跃度 |

总分计算：

```text
总分 = 各维度有效子分的加权结果 - 硬性风险扣分
```

当信息缺失时，不把缺失项直接计为零；系统应降低置信度，并显示“信息不足”。

#### FR-MATCH-002 硬性条件

用户可将条件设置为“必须满足”或“偏好”。必须条件不满足时，岗位仍可保存，但默认进入“不推荐”分组，并明确失败原因。

#### FR-MATCH-003 证据映射

每项 JD 要求映射到以下类别之一：

- 强证据：有直接、已确认且可追问的经历。
- 弱证据：相关但表达不足或缺少结果。
- 可迁移能力：来自其他岗位或场景。
- 学习/作品证据：来自课程、个人项目或作品。
- 真实缺口：当前没有证据。

#### FR-MATCH-004 评分输出

岗位详情必须展示：总分、五维子分、置信度、推荐结论、命中证据、关键缺口、风险项、需要补充的问题和建议使用的简历版本。

禁止只显示单一分数而不提供依据。

#### FR-MATCH-005 重算与版本

评分结果记录评分规则版本、模型名称、提示词版本和简历母版版本。用户更新资料后可批量重算，旧结果保留以便比较。

### 5.5 岗位定制简历

#### FR-RESUME-001 一岗一版

每个目标岗位生成独立简历版本，并与岗位 ID、JD 快照和母版版本绑定。不同岗位版本互不覆盖。

#### FR-RESUME-002 生成约束

- 只能使用 `confirmed` 事实。
- 不得新增不存在的公司、项目、技能、数据或职责。
- 不确定的量化结果必须先询问用户。
- 团队成果不得全部归因于个人。
- 课程项目不得包装为公司工作经历。
- 关键词必须附着在真实行动或成果上，不允许堆词。

#### FR-RESUME-003 生成内容

系统可提议：职业摘要、经历排序、项目选择、bullet 改写、技能排序、关键词补充和删减建议。每项改动必须附修改理由和引用的事实 ID。

#### FR-RESUME-004 差异审阅

采用逐条差异视图展示原文、建议文本、修改理由、命中 JD 要求和事实来源。用户可以接受、拒绝或编辑单项修改。

#### FR-RESUME-005 版本管理

简历版本状态包括：草稿、待确认、已确认、已导出和已投递。系统保留历史版本，并支持复制为新岗位版本。

### 5.6 简历排版与导出

#### FR-FORMAT-001 编辑器

支持实时预览、章节排序、字段编辑、页面边距、字号、行距、强调色和模板切换。首版至少提供：ATS 单栏、现代单栏和紧凑技术型三种模板。

#### FR-FORMAT-002 ATS 检查

检查项包括：

- 文本是否可选择和提取。
- 是否使用复杂表格、图片文字、文本框或多栏导致解析异常。
- 标题是否为常见章节名称。
- 联系方式是否位于正文可解析区域。
- 是否存在关键词堆叠、隐藏文字或异常字符。
- 是否出现页尾截断、重叠、空白页或内容溢出。

#### FR-FORMAT-003 导出

支持导出 PDF、DOCX 和结构化 JSON。导出文件名默认包含姓名、岗位、公司和日期，但必须清理非法文件名字符。

验收标准：

- PDF 非空且正文可提取。
- DOCX 可在 Microsoft Word 中打开。
- 页面没有可见重叠、截断或意外空白页。
- 导出文件与预览内容一致。

### 5.7 岗位中心与投递看板

#### FR-BOARD-001 岗位列表

支持按平台、总分、子分、城市、薪资、公司、发布日期、状态和关键词筛选。支持收藏、忽略、加入黑名单和批量重新评分。

#### FR-BOARD-002 投递状态

状态流转：

```text
待分析 -> 待定制 -> 待确认 -> 待投递 -> 已投递
                                   -> 沟通中
                                   -> 面试中
                                   -> Offer
                                   -> 已结束
```

每次投递记录岗位、使用的简历版本、投递日期、平台、备注和后续反馈。

#### FR-BOARD-003 人工确认

系统可以打开原岗位链接、复制打招呼文案和准备附件，但 MVP 不代替用户点击最终发送或投递按钮。

### 5.8 设置与诊断

支持设置 AI 服务商、模型、API 地址、密钥、代理、采集限速、浏览器路径、数据目录、导出目录和平台开关。

提供平台健康检查，包括：浏览器是否可用、登录态是否有效、选择器是否匹配、最近一次成功时间和失败原因。

## 8. AI 能力规范

### 8.1 模型调用原则

- 支持 OpenAI-compatible、Anthropic 和本地模型接口。
- 所有关键输出使用结构化 JSON，并通过 Schema 校验。
- 模型失败时保留规则评分和基础功能，不阻塞岗位采集与浏览。
- 低置信度内容必须标记，不允许静默进入最终简历。
- 每次生成记录模型、温度、提示词版本和输入摘要。

### 8.2 AI 任务拆分

1. JD 结构化：职责、硬条件、加分项、隐性要求和风险。
2. 证据检索：从已确认事实中寻找对应经历。
3. 评分解释：解释规则结果，不可随意改写确定性硬条件。
4. 简历改写：仅使用引用的事实 ID。
5. 真实性审查：逐条检查生成内容是否有事实来源。
6. ATS 审查：检查内容和结构，不宣称可保证通过任何 ATS。

### 8.3 生成失败处理

出现 JSON 解析失败、超时、额度不足或模型拒绝时，系统应展示明确错误，并允许重试、更换模型或退回规则模式。不得用空结果覆盖已有内容。

## 10. 非功能需求

### 10.1 隐私与安全

- 默认所有简历、岗位、评分和投递数据只保存在本机。
- API 密钥使用 Windows 凭据管理器或本地加密存储，不写入日志和 Git。
- 平台登录态保存在平台专用浏览器目录，不导出明文 Cookie。
- 日志默认脱敏手机号、邮箱、Cookie、Token 和完整简历内容。
- 支持一键备份和彻底删除本地数据。

### 10.2 性能

- 岗位库包含 10,000 条数据时，常用筛选响应时间不超过 500ms。
- 500 条岗位的规则评分在普通个人电脑上不超过 30 秒。
- AI 深度评分默认只处理规则预筛后的 Top N 岗位，并展示预计调用量。
- 采集、评分和导出任务不得阻塞界面操作。

### 10.3 可靠性

- 平台适配器故障相互隔离。
- 所有长任务支持取消、重试和断点恢复。
- 数据写入使用事务；应用异常退出后不丢失已完成记录。
- 数据库升级前自动备份。
- 平台页面结构变化时展示诊断信息，不静默返回“0 条岗位”。

### 10.4 可维护性

- 平台选择器和解析规则应集中管理并有夹具测试。
- 每个平台保存脱敏 HTML/API 样本用于回归测试。
- 评分规则、模型提示词和导出模板均需版本化。
- 核心业务逻辑不得直接依赖具体平台字段。

### 10.5 合规要求

- 产品只处理用户有权访问的页面内容。
- 尊重平台频率限制和访问限制。
- 不提供绕过验证码、设备验证或封禁的功能。
- 自动化在验证页面出现时必须停止。
- 最终投递和消息发送默认由用户主动确认。

## 11. 产品指标

### 11.1 核心指标

- 上传原始简历后成功生成简历母版的比例。
- 从上传到进入岗位匹配流程所需的人工补充字段数量。
- 完成简历母版并确认事实的用户比例。
- 每次采集成功写入的有效岗位数。
- 重复岗位合并准确率。
- 用户收藏或进入定制流程的高分岗位比例。
- AI 修改建议接受率和人工修改率。
- 简历导出成功率及 PDF 校验通过率。
- 从发现岗位到生成定制简历的完成率。
- 投递后获得沟通或面试的比例，由用户自愿记录。

### 11.2 质量指标

- 在标准文本型 PDF/DOCX 测试集上，章节识别准确率不低于 95%，关键字段准确率不低于 90%。
- 已被正确识别的字段要求用户重复录入的数量必须为 0。
- 未经确认事实进入最终简历的数量必须为 0。
- PDF 空白、截断、重叠和不可提取文本问题必须为 0。
- 平台异常被错误报告为“无岗位”的比例低于 1%。
- 同一岗位重复入库率低于 5%。

## 12. MVP 验收标准

MVP 发布必须同时满足：

1. Windows 环境可通过一个启动入口运行。
2. 用户可以在首次引导中直接上传 PDF 或 DOCX 原始简历，并自动生成结构化母版。
3. 已识别信息不要求重复填写；用户可以批量确认，只处理低置信度、冲突或关键缺失项。
4. 原始简历、解析结果、事实和母版之间可以相互追溯，重新上传不会静默覆盖已确认内容。
5. BOSS、智联、猎聘三个适配器可独立启停和健康检查。
6. 用户能通过专用浏览器手动登录，程序不要求导出明文 Cookie。
7. 在平台允许访问且页面正常时，每个平台可采集列表和完整 JD。
8. 岗位统一入库并按平台 ID、URL 和组合指纹去重。
9. 每个岗位展示五维评分、置信度、证据和扣分理由。
10. 至少支持一份母版派生三个互不覆盖的岗位简历版本。
11. 每条生成内容都能追溯到已确认事实，缺少事实时主动提问。
12. 用户可逐条接受或拒绝修改，并可恢复历史版本。
13. 至少三套模板可导出 PDF 和 DOCX。
14. 导出 PDF 通过文本提取、页面数量、空白页和溢出检查。
15. 投递看板能记录岗位、所用简历版本、状态和反馈。
16. 验证码、登录失效和模型故障均有明确状态与恢复入口。
17. 最终投递和消息发送未经用户确认不得执行。
18. 安装包和仓库包含许可证、第三方声明和隐私说明。

## 14. 风险与应对

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| 平台页面频繁改版 | 采集失败 | 插件隔离、样本回归测试、健康检查、URL/CSV 备用导入 |
| BOSS 反自动化严格 | 登录验证或账号限制 | 有头模式、低频、专用配置、验证即停、不默认定时运行 |
| AI 编造经历 | 简历失真和面试风险 | 事实 ID 引用、确认状态门禁、生成后独立真实性审查 |
| AI 评分不稳定 | 岗位排序不可相信 | 硬规则主导、固定评分版本、展示子分和置信度 |
| 简历格式影响 ATS | 简历无法解析 | ATS 单栏默认、文本提取测试、渲染截图检查 |
| Cookie/API 密钥泄露 | 账号和隐私风险 | 专用浏览器目录、系统凭据存储、日志脱敏、Git 忽略 |
| 无许可证代码混入 | 无法合法发布 | 只复用 MIT/Apache-2.0 代码，其余功能重新实现或获取授权 |
| 模型调用成本过高 | 用户无法持续使用 | 规则预筛、Top N 深度分析、缓存和调用预算提示 |

## 15. 待确认决策

以下决策不阻塞 MVP 设计，但需在开发前确认：

1. 产品最终名称和仓库名称。
2. 首版是否仅支持单用户本地运行，还是同时支持局域网多用户。
3. 默认 AI 服务商以及是否必须支持完全本地模型。
4. BOSS、智联、猎聘之外，第四个平台优先选择拉勾还是前程无忧。
5. 是否需要在 MVP 中加入飞书多维表格同步。
6. 是否需要将简历排版编辑器完整复用 Reactive Resume，或只复用其数据结构与导出模块。
7. 是否公开发布源代码；若公开，是否采用建议的 Apache-2.0 许可证。

## 16. 默认产品决策

如无额外调整，项目按以下默认方案进入设计和开发：

- Windows 本地单用户应用。
- 首版平台为 BOSS、智联和猎聘。
- TypeScript 单一技术栈，SQLite 本地数据库。
- 复用合法许可的简历渲染与校验能力，其他模块重新实现。
- 默认 ATS 单栏简历，不默认使用照片和复杂双栏布局。
- AI 只生成建议，所有事实和最终投递均需用户确认。
- 不实现验证码绕过和无人值守批量投递。
